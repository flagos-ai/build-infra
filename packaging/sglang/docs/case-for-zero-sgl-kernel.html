01 · 现状官方 sglang 为什么装不上

  1. CUDA 版锁死 torch 版本。它声明 torch==2.13.0，而 runtime 各后端 验证过的是 2.8~2.11。直接安装会覆盖精心匹配的依赖矩阵。
  2. CUDA 版强制捆绑内核编译件。sglang-kernel 是随硬件架构、编译器、 Python 版本强绑定的二进制组件，没有通用版可装。
  3. 官方非 CUDA 版不完整。基础依赖缺了约 40 项，且没有任何硬件算子 接线——装了也无法启动服务。
  4. 厂商平台官方不覆盖。MetaX、mthreads、enflame、kunlunxin 等没有 官方内核编译件；"等上游提供"逐平台不现实。

结论：官方没有一条安装路径能直接进 FlagOS runtime，必须先解决"硬件算子从哪来"。

02 · 路线对比四条路，收敛到一条

路线做法代价
官方 wheel 原样装 CUDA 版直接 pip install 破坏依赖矩阵，装不上
每后端一条镜像 每个厂商单独出一套镜像 镜像数量随厂商线性增长
每平台自编内核 各厂商编译算子子集 组合数量随维度相乘：厂商 × 版本 × torch × Python
选定 零内核路线 上游 wheel + 导入替身 + 算子走 flag_gems 一次性接线，全平台共用

自编内核的成本有实证：在 MetaX 上编译过 10 个算子的子集，需改源码、 自写注册、逐能力调编译参数；每换一个厂商、一个 sglang 版本、一个 torch 版本都要 重来一遍——成本随组合数量增长，不是线性增加。

03 · 为什么可行六个原理，环环相扣

1

sglang 核心并不真正需要内核组件

sglang 启动时会检查 sglang-kernel 是否存在，但对受支持的厂商平台， 实际计算并不经过它：注意力等关键路径落到平台自身实现，其余算子走算子库。 因此只需一个纯 Python 的"导入替身"让它通过启动检查——替身不做任何计算，只让程序 认为组件在。MetaX 端到端跑通，证明这一点成立。

还有一个佐证：上游 0.5.18 的源码里已经有一份独立的 非 CUDA 构建配置（pyproject_others.toml）——上游自己就在把 非 CUDA 平台当作正式的构建路径推进，本路线顺着这个方向接线，而不是另起炉灶。

2

硬件算子由算子库按厂商提供

flag_gems 本就是按厂商分发算子的库（内置 15 个厂商目录），与 sglang 的厂商后端 一一对应——"每厂商提供算子实现"替代了"每厂商提供编译件"。逐项核对迁移面后： 约三分之二算子已有现成实现，直接接线即可；剩余分两级——"改调已有实现"与 "少数专用算子移植"，真正需要新写的集中在个别厂商的专用注意力算子。

3

端到端已经跑通

MetaX 平台服务正常启动、请求正常返回 token。两套编译器路径——FlagTree 与 Triton（下文简称 F/T）——各 3 次请求全部通过。判据：HTTP 200、返回 144 个 token、 采样后端为 pytorch。

5

版本选最新：0.5.18，而不是大家在用的 0.5.11 / 0.5.12

0.5.11 / 0.5.12 是旧镜像线的选择；0.5.18 是这条统一路线的头部版本，也是逐级 验证链（0.5.10 → 0.5.12 → 0.5.18）的最后一环。选它而不是旧版本，理由如下。

版本处境为什么不是它
0.5.11 CUDA 依赖链整体跳到 cu13（torch 2.11+cu130） 与 runtime 验证过的 torch 2.8~2.11 矩阵错配，只对得上 cuda13.3 后端
0.5.12 上游 0.5.16 引入 circular-import 回归，旧镜像线被迫钉死此版本 是为绕开回归的权宜；选它意味着打包起点落后两个版本
0.5.18 选定 最新；MetaX 上双路径 E2E 全过 —

为什么最新反而稳妥。第一，路线不靠躲版本成立： 0.5.16+ 引入的 circular-import 回归在 0.5.18 上实证未触发——最新代码库能过， 说明路线对上游更新不敏感，而不是挑了个旧版绕开；第二，升级是增量不是重来： 0.5.10 → 0.5.12 → 0.5.18 每级只花一次双路径 E2E 的验证成本，打包 0.5.18， 下一次上游升级前可用时间最长；第三，0.5.11 到 0.5.18 之间上游累计的修复全部包含。

6

改动量可控：一次构建，其余逐端实测

MetaX 端到端落地的改动可以数出来：约 7 处——1 个导入替身包、2 处 wheel 构建期补丁、1 处插件修复、3 个启动开关。按能否平移分三类：

类别MetaX 实际内容到其他后端
全后端共用，一次建成 导入替身（随 sglang 版本生成）、统一构建/repack 管线、依赖审计门禁 直接复用，不按后端重做
逐端实测确认，微调即可 3 个启动开关、3 处 JIT 缺口补丁 每端核对是否触发；触发则照修，不触发则略过
实测发现才修 算子库覆盖缺口：MetaX 为 0 已按 A/B/C 分级；多数端只需接线

工作量怎么估。约一半内容（导入替身、构建管线、审计门禁） 全后端共用，只随 sglang 版本重生成；另一半是"确认是否触发"的核对项，每个新后端的 成本是核对与微调，按"处"计而不是按开发量计。已知需要算子移植的只有个别厂商： enflame 2 个、kunlunxin 一类专用算子，MetaX 本身为 0。

04 · 为什么走这条路四条理由，逐条说明

  1. 官方覆盖不了全量平台。目标 13+ 厂商，非 NVIDIA 平台没有官方内核 编译件；路线不能建立在"等厂商提供"上。
  2. 全栈算子收敛到一份。硬件算子统一由 runtime 内置的算子库提供， 与 vllm、megatron 共用同一份——全栈只有一份算子依赖。
  3. 与 vllm 线同一模式。vllm 已全线"wheel 不含硬件算子 + 插件 + 单步安装"；sglang 走同一模式，团队只需维护一套打包心智，镜像线不随应用增长。
  4. 为未来留替换空间。导入替身只占"启动检查"一层；某平台日后有了真正的 内核编译件，替换 wheel 即可，打包与安装方式不变。

05 · 风险与处置已知风险与应对

风险现状处置
性能 约 4 token/s 未优化；低于自编内核基线（约 40），跨版本不完全可比 正确性优先；差距属调优问题，可后续优化；验收口径待定
覆盖缺口 个别厂商专用算子 迁移面已逐项核实，缺口集中且明确 已有实现的接线；少数专用算子移植进算子库；逐厂商验证
验证广度 目前仅 MetaX 闭环 其余厂商未验证 逐厂商双路径验证门禁，与 vllm 线同一机制
版本回归 上游升级引入新问题 MetaX 上未触发 其余厂商验证时一并覆盖

06 · 待团队拍板三件事，需要大家定

  1. 是否立项，以及从哪个厂商开始推进（hygon / enflame 先行？）
  2. 缺口算子的维护归属：由算子库上游维护，还是我们的补丁维护。
  3. 性能验收口径：逐厂商双路径端到端 + 吞吐对比。

这是当前覆盖全量非 NVIDIA 平台的 sglang 分发方式，已端到端实证；其余路线各有明显制约。
