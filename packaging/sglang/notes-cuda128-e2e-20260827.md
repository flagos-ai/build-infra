## 环境

- 节点：h20（8×H20 97GB）；容器：`sglang-nv128-serve`（镜像 `sglang-probe:0.1`，从 build-infra runtime nvidia-cuda12.8 派生，venv `/flagos`，python3.12 via uv）

## 结论（临时，待降级验证后修订）

1. **§4.3 torch 错配预言实证**：sglang==0.5.11 依赖链把容器内 build-infra runtime 的 torch **2.10.0+cu128 整体替换为 torch 2.11.0+cu130**。容器呈 cu13（cuda-python/cudart/cublas/cudnn/nccl/nvrtc 13.x）+ cu12 残留的混合栈。→ sglang 0.5.11 不适合 cuda12.8 后端（torch 链连带升到 cu13）；按用户判断更适合 cuda13.3。
2. **cuda 后端落地的前提障碍 = 容器无 nvcc**（节点 `/usr/local/cuda` 无 `bin/`；`nvidia-cuda-toolkit 13.0.2` 只是 Python DSL umbrella，不带 nvcc）。sglang JIT kernels（qknorm/kvcache/resolve_future_token_ids，tvm_ffi+ninja，`-gencode=arch=compute_90,code=sm_90`）与 flashinfer（batch_prefill，sm_90a）都硬编码 `/usr/local/cuda/bin/nvcc`，无 nvcc 即 SIGQUIT。
3. **nvcc 修复配方**（容器内，aliyun 镜像 + unset proxy；版本必须配套）：
   - `pip install nvidia-cuda-nvcc==13.3.73 nvidia-nvvm==13.3.73 nvidia-cuda-cccl==13.3.3.4.1`
   - 坑 A：13.2.51 的 ptxas 只支持 PTX 9.2，而 13.3 的 nvcc 生成 PTX 9.3 → 必须 nvcc+ptxas 同版本（都 13.3.73）。
   - 坑 B：`<nv/target>` 头不在 nvcc 包里，在 `nvidia-cuda-cccl` 包里（装完进 `cu13/include/`）。
   - 坑 C：`/usr/local/cuda/bin/nvcc` 直接软链不行，要 wrapper：`export CUDA_PATH=<cu13>; exec <cu13>/bin/nvcc "$@"`（否则找不到 headers/libdevice）。
   - 坑 D：`-lcudart` 找不到 → `cu13/lib/libcudart.so` dev symlink + `/usr/local/cuda/lib64` 重指 `cu13/lib`。
   - headers：`/usr/local/cuda/include` 重指 `cu13/include`（cu12 的 targets include 只含 nvtx，无 cuda_runtime.h 等）。
4. **插件真实参与**：graph capture 期间 `Op 'rms_norm'/'rotary_embedding'/'silu_and_mul' using 'default.flagos' (mode=fallback-enabled)` —— sglang_fl Layer-1 dispatch 把 ATen 算子路由到 flag_gems default.flagos 内核。
5. **E2E 推理闭环**：`/v1/chat/completions` 200，Qwen3-4B 正常生成（含 `<think>` reasoning），decode `cuda graph: True`。GPU 0 峰值 ~71GB。

## 降级版本检索结论 + ABI 实测（2026-08-27）

**结论：sglang 0.5.10 最适合 cuda12.8 后端，且 torch 必须降级 2.9.1（不可保留 2.10.0）。** —— 它们锁的是 torch==2.9.1，而 **PyPI 默认 torch 2.9.1 wheel 内置 cu128**（sglang 官方 CI `scripts/ci/cuda/ci_install_dependency.sh` 注释原文："PyPI's torch 2.9.1 bundles cu128"，且明确说不能换 cu129 torch，否则 "breaks sgl_kernel ABI"）。整条链留在 CUDA 12.x 族内，正好服务 cuda12.8 后端；0.5.11 则整链升 cu13（本次实测已证）。

**首选 = 0.5.10**：cu12 线最后版本（0.5.11 跳 cu13），与 0.5.9 同链（torch 2.9.1 cu128 + cuda-python 12.9 + flashinfer cubin），flashinfer 更新（0.6.7.post2）；内核包改名 sglang-kernel 0.4.1（0.5.10 参考环境：Dockerfile CUDA_VERSION=12.9.1，CI 安装走 PyPI 默认 cu128 torch）。0.5.9 = 同链 fallback。

版本 → 锁定的链条（来自各 tag 的 `python/pyproject.toml` 源码，PyPI wheel 元数据为空，不具参考性）：

| sglang | torch | cuda-python | 内核包 | flashinfer | cu12.8 适配 |
|---|---|---|---|---|---|
| 0.5.11 | 2.11.0 | >=13.0 | sglang-kernel 0.4.2 | cu13 代 | ❌（实测 torch 2.10+cu128→2.11+cu130） |
| 0.5.10 | 2.9.1 | ==12.9 | sglang-kernel 0.4.1 | flashinfer_python+cubin 0.6.7.post2 | ✅ |
| 0.5.9 | 2.9.1 | ==12.9 | sgl-kernel 0.3.21 | flashinfer_python+cubin 0.6.3 | ✅ |
| 0.5.8 | 2.9.1 | ==12.9 | sgl-kernel 0.3.21 | flashinfer_python+cubin 0.6.1 | ✅ |
| 0.5.7 | 2.9.1 | 无 pin | sgl-kernel 0.3.20 | ? | ✅ |
| 0.5.4/0.5.3 | 2.8.0 | 无 pin | ? | ? | ✅（torch 2.8 默认 cu128） |

关键事实：

1. **torch 链连带降级但不漂出 cu128**：装 0.5.9/0.5.10 会把容器内 torch 2.10.0+cu128 → PyPI torch **2.9.1（内置 cu128）**，版本降、CUDA 族不变 —— 正是目标状态。
2. **flashinfer 0.6.1~0.6.7 走 `flashinfer_cubin`（py3-none-any 纯预编译包）**，无 sm_90a JIT → 0.5.11 的 `--attention-backend triton` 绕过项在 0.5.9/0.5.10 上可能不需要（可先保持 triton 跑通，再试 flashinfer 原生）。
3. **sgl-kernel 0.3.21 / sglang-kernel 0.4.1 都是 cp310-abi3 通用 wheel**（x86_64+aarch64），面向 torch 2.9.x ABI 预编译；sgl-kernel→sglang-kernel 改名发生在 0.5.10。
4. **nvcc 仍是前提**：sglang 自带 jit_kernel（qknorm/kvcache/resolve_future_token_ids，tvm_ffi+ninja）仍需 nvcc；但 0.5.9 触发面小于 0.5.11（flashinfer 预编译、sgl-kernel 预编译覆盖更全）。已装 cu13 nvcc 13.3.73 wrapper 配方仍适用（gencode=sm_90 是架构级，cubin 可被 cu12.8 运行时加载）。

### torch 不降级 = 不可行（节点实证 2026-08-27，非推测）

干净 runtime 容器（torch 2.10.0+cu128）`pip install sglang-kernel==0.4.1 --no-deps` 后 `import sgl_kernel`：

```
ImportError: /flagos/lib/python3.12/site-packages/sgl_kernel/sm90/common_ops.abi3.so:
  undefined symbol: _ZN3c104cuda29c10_cuda_check_implementationEiPKcS2_ib
```

- demangle = `c10::cuda::c10_cuda_check_implementation(int, char const*, char const*, int, bool)` —— torch 2.9.1 的 torch_cuda 导出该符号，torch 2.10.0 缺失 → **跨 minor torch C++ ABI 断**；`.abi3.so` 只覆盖 Python C-API，不覆盖 torch 自身 ABI。这正是官方 CI 注释 "We cannot replace torch with cu129 (breaks sgl_kernel ABI)" 的另一面实证。
- 想留 torch 2.10.0 只能对 sglang-kernel 源码对 2.10 头重编，脱离 vendor 预编译 wheel 模型 —— 不做。
- **定论：torch 降到 2.9.1**。PyPI 默认 torch 2.9.1 捆绑 cu128，CUDA 族不变（仍 12.x），cuda12.8 后端语义不受影响；0.5.10 参考环境（Dockerfile CUDA 12.9.1 + PyPI 默认 cu128 torch）正是此组合，非妥协。

## 0.5.10 节点实测全链（2026-08-27）：E2E 闭环

> 下方原"下一步"已完成。0.5.10 全链在 h20 节点实测闭环，F/T 双路径均通过。

### 安装链（容器内实测，aliyun 镜像）

`pip install sglang==0.5.10` 连带：torch 2.10.0+cu128 → **torch 2.9.1（PyPI 默认 cu128）**、
cuda-python 12.9.0、cuda-bindings 12.9.7、sglang-kernel 0.4.1、flashinfer_python+cubin 0.6.7.post2、
transformers 5.3.0、triton 3.5.1。CUDA 族全程 12.x，与 0.5.11 的整链跳 cu13 形成对比。

### 0.5.10 无 plugin 框架（与 0.5.11 结构差异）

0.5.10 无 sglang_fl 插件层，不存在 0.5.11 的 Layer-1 ATen dispatch（default.flagos）。
"F 路径"含义随之变化：F = FlagTree 作为 triton 编译器（PYTHONPATH=/opt/flagtree，3.6.0），
不是 flag_gems dispatch。sglang 自带 tvm-ffi JIT 内核（qknorm/kvcache/resolve_future_token_ids，
CUDA C++/ninja）仍需 nvcc 13.3 wrapper —— 此前判断成立。

### flashinfer sampling JIT = 0.5.10 硬阻塞（已解决）

**修正此前判断**："0.5.9/0.5.10 flashinfer 纯预编译无 JIT" 是错的。flashinfer_cubin 预编译
**只覆盖 attention**，sampling 仍走 JIT：decode 经 `top_k_top_p_sampling_from_probs` → ninja
编译 `cached_ops/sampling/`（csrc_sampling.cu 等 4 TU，`-gencode=arch=compute_90a,code=sm_90a`）
→ 失败即 "SIGQUIT received" 整服退出（exit 137）。0.5.11 上 `--attention-backend triton` 绕过
在 0.5.10 不适用：attention 可绕，sampling 绕不掉。

**根因**（非 flashinfer bug）：cu13 include 树里的 `nvidia-cuda-runtime` 13.0.96
（CUDART_VERSION=13000）与 nvcc 13.3.73 错配 → CCCL 兼容检查 `cuda_toolkit.h:41` #error
（nvcc major.minor 必须等于 CUDART_VERSION 的 major.minor）。

**解法**（容器内，aliyun）：`pip install nvidia-cuda-runtime==13.3.29`（CUDART=13030，与 nvcc
13.3.73 对齐；aliyun 无 cu12.9 nvcc/nvvm/cccl，只能走 13.3 一致线）。serve 启动 env 三件套：

- `CUDA_HOME=/flagos/lib/python3.12/site-packages/nvidia/cu13`（flashinfer 依此找 nvcc+头+cccl）
- `LD_LIBRARY_PATH` 前置 `.../nvidia/cu13/lib`（编译出的 sampling.so 链接 `libcudart.so.13`，
  宿主 /usr/local/cuda/lib64 只有 cu12 的）
- `/usr/local/cuda/bin/nvcc` = 13.3 wrapper（之前配方不变）；sglang tvm-ffi JIT 缓存命中不重编

### F/T 双路径 E2E 矩阵（Qwen3-4B，256 token 全生成含 <think>）

| 路径 | 编译器 | attention | cuda graph | decode tok/s | 结果 |
|---|---|---|---|---|---|
| F | FlagTree 3.6.0（/opt/flagtree） | fa3（flashinfer） | True | ~248 | ✅ 200 OK，0 SIGQUIT |
| F | FlagTree 3.6.0（/opt/flagtree） | triton | True | ~260 | ✅ 200 OK，0 SIGQUIT |
| T | vendor triton 3.6.0（/opt/triton） | triton | True | ~260 | ✅ 200 OK，0 SIGQUIT |

三路均验证：sampling JIT 成功（每个容器首次 sampling 即编译通过，证明修复在镜像层
`sglang-0510-fix2:0.1` 而非缓存）；FlagTree / vendor triton 各自完成 triton 内核 JIT。
镜像 `sglang-0510-fix2:0.1` = nvcc 13.3 wrapper + cudart symlink + `nvidia-cuda-runtime==13.3.29`。

**结论**：0.5.10 在 cuda12.8 后端干净闭环（整链 CUDA 12.x；nvcc 13.3 仅作 JIT 编译器，cubin
为 sm_90a 架构级，可被 cu12.8 运行时加载）。torch 2.9.1 为 PyPI 默认 cu128，无 cu13 运行时组件驻留。
