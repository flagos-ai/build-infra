vLLM 0.32.0 的 torch >= 2.13 是否严格

评估 vLLM 0.32.0（pyproject.toml 声明 torch == 2.13.0、requires-python >=3.11） 能否落在一个 torch 2.11 / Python 3.10 的栈上。结论：两个下限都是上游的打包声明，不是 API 契约——torch 2.11 可通过 empty 构建与 import，Python 3.10 可经一条纯 import 改写补丁跑通到 serve 入口。

范围：静态审计 + 本机 import/构建/符号探针 未做：Linux 上的 serve 实测（§8） torch 2.11 可通过 empty 构建与 import py3.10 empty wheel 已构建并安装成功 py3.10 可由一条 39 文件补丁绕过

§ 1
结论

torch 下限

torch ≥ 2.13 不是 API 契约

torch >= 2.13 是上游的打包 / QA pin，不是 API 契约。vLLM 全树没有一处 因为 torch 版本低而拒绝启动；每一处版本判断都在为旧 torch 打补丁，或探测新 torch 的优化开关。torch 2.11 能通过 empty 构建与 import，失去的只有 inductor 优化。

Python 下限

Python ≥ 3.11 不是运行时依赖

requires-python >=3.11 是 0.32 一次 import 清理的副产品：它把五个名字 （Self / Never / Required / NotRequired / assert_never）从 typing_extensions 收回到 typing，而这些名字 3.11 才进 typing。全树没有用到任何 3.11 独有的运行时特性，一条纯 import 改写补丁 （37 个文件 + 2 个 datetime 文件）即可在 py3.10 上跑到 serve 入口； py3.10 的 empty wheel 已构建并安装验证（§6.4）。

因此 0.32.0 落不下来的原因不在 torch / Python，而在另外两处硬边界：CUDA 侧运行时依赖的版本天花板， 以及 py3.10 路线所要求的补丁常驻（§6）。

§ 3
版本门控的语义：兜底旧 torch，而非索要新 torch

同一组文件（env_override.py、compilation/{compiler_interface,backends}.py、 config/compilation.py）在三个版本上的版本字面量直方图：

版本门控字面量
0.24.02.12.0.dev×6, 2.10.0×4, 2.9.0×2, 2.9.0.dev×2, 2.11.0×2, 2.9.1, 2.6, 2.13.0.dev, 2.11.0.dev
0.28.0与 0.24.0 完全相同
0.32.0同上，另加 2.16.0.dev×1

0.32.0 相对 0.28.0 只多一个门控点（env_override.py:968，pattern-matcher 补丁的上界）， 没有把任何门控抬到 2.13。2.13.0.dev 那一处在 0.24.0 就已存在，内容是 compile_kwargs["donate_graph_module"] = True——新 torch 的优化开关，旧 torch 上跳过。

反向证据更直接：

  • env_override.py:716 注释原文 "minimum supported torch is 2.12"；
  • env_override.py 中 2.9 / 2.10 / 2.11 的补丁块（constrain_to_fx_strides、 FxGraphCachePickler、cpp indirect_assert）全是为旧 torch 补 API；
  • compilation/backends.py:604 has_tuple_return = is_torch_equal_or_newer("2.12.0.dev") ——2.11 的 split_module 无此 kwarg，故旧 torch 上主动不传。

实测：torch 2.11.0 下 import 0.32.0

在 torch 2.11.0 环境里对未改动的 0.32.0 源码树执行 import vllm，成功并报出 自己的版本号 0.32.0。逐符号扫描的对照结果：

两份缺失集合的差集只有两条：

  • torch.utils.cpp_extension.CUDA_HOME —— 探测脚本的 artifact，非 vLLM 引用；
  • torch.accelerator.empty_host_cache —— 0.32.0 已用 try/except AttributeError 包住 （distributed/parallel_state.py:2555-2559）。

其余 22 条在 2.13 上同样缺失，因此不构成版本判别项。

2.13 新增、2.11 缺失的私有 API 只有三处，且都有退路：

API使用点2.11 上的行为

值得注意：0.32.0 在这一点上比 0.24.0 / 0.28.0 对旧 torch 更友好。0.24 / 0.28 直接读 PYTORCH_CUDA_ALLOC_CONF 环境变量并恢复 SIZE_MAX，0.32 改走 allocator settings，而它的回退分支（torch.cuda.memory._snapshot()）在 torch 2.11 的 C++ （torch/csrc/cuda/Module.cpp）里已经存在。
§ 5
torch 2.11 上失去的东西

全部是 inductor 编译优化，不影响正确性：

  • donate_graph_module（≥2.13.dev）
  • split_module(tuple_return=True)（≥2.12.dev）
  • pregrad pass 跳过（≥2.12.dev）——旧 torch 上由 monkeypatch torch._inductor.compile_fx._recursive_pre_grad_passes 达成同等效果
  • mega-AOT 默认开启（≥2.12.dev）
  • assert 合并成一次（≥2.12）——旧 torch 上 config/compilation.py:924-943 把 size_asserts / alignment_asserts / scalar_asserts 降到 "仅 DEBUG 打开"，即断言密度下降但语义不变

triton 侧不成问题：torch 2.11 要求 triton==3.6.0，torch 2.13 要求 3.7.1， 但后者内部下限是 _TRITON_MINIMUM_VERSION_MINOR = 6 （torch/_native/triton_utils.py:29），即 2.13 容忍 triton 3.6——这正是 AMD 栈保留 FlagTree 0.7.0（内含 triton 3.6）的依据。

§ 6
真正的阻塞

6.1 Python 下限：0.32.0 声明 >=3.11，但可绕过

0.24.0 / 0.28.0 是 >=3.10，0.32.0 抬到 >=3.11,<3.15。这个声明本身 是硬的（pip 在 metadata 阶段就拦下 py3.10），但它约束的东西不是 3.11 的能力，而是 3.11 才补齐的 typing 名字，实测可绕过 —— 见 §6.4。

Python后端原样声明加补丁后

6.2 CUDA 侧运行时依赖天花板

0.32.0 的 requirements/cuda.txt 相对 0.24.0 新增一整批 NVIDIA 专属依赖，全部落在 config.yaml remove_cuda_only 里：torchcodec>=0.14、 PyNvVideoCodec==2.0.4、flashinfer-python==0.7.0.post1、 tilelang==0.1.12、nvtx==0.2.15、instanttensor>=0.2.2、 nvidia-cutlass-dsl[cu13]==4.8.0、quack-kernels==0.6.5、 tokenspeed-mla==0.2.15、humming-kernels[cu13]==0.1.17。非 CUDA 后端拿不到这些的 vendor 变体。

requirements/common.txt 的公共面同样上抬：transformers >= 5.16.1, < 5.20.0、 huggingface_hub >= 1.31.0、tokenizers >= 0.23.2、 openai >= 2.25.0、pillow >= 12.3.0、mcp >= 2.0.0, < 3.0.0、 oss-harmony >= 0.0.11。

6.3 升 torch 自身的 ABI 代价

已经付过一次：AMD 从 torch 2.11.0+rocm7.2 迁到 2.13.0+rocm7.2 时，torch 2.13 不再导出 materialize_cow_storage（改为 StorageImpl.h 内联），迫使 flagcx 0.14.1+rocm7.2.4 重新构建。这类代价按后端各付一次，与 vLLM 的版本号无关。

6.4 Python 下限可绕过：一条 39 文件的 import 改写

把 py3.11 相对 py3.10 新增的运行时特性全树扫一遍，命中为零：

特性命中
ExceptionGroup / except*0
asyncio.TaskGroup / asyncio.timeout0
tomllib / enum.StrEnum / contextlib.chdir / itertools.batched / hashlib.file_digest0
PEP 695 泛型语法（3.12）0

唯一的 sys.version_info 闸门是 distributed/utils.py:41： USE_SCHED_YIELD = sys.version_info[:3] >= (3, 11, 1)。它自带回退 （time.sleep(0)），注释也写明原因（3.11.1 起 os.sched_yield 才释放 GIL）。 实测在 py3.10 上该值为 False，走回退分支。

真正构成间隔的是五个 typing 名字和一个 datetime 常量， 且改法极廉价：

缺什么规模改法
typing.Self / Never / Required / NotRequired / assert_never37 个文件改为从 typing_extensions import
datetime.UTC2 个文件（snapshot/runtime.py、usage/usage_lib.py）datetime.timezone.utc
零成本的关键：0.32 的 requirements/common.txt:30 本来就声明 typing_extensions >= 4.10，而 4.10 已含这五个名字 —— 这份依赖一直在装，只是没人用。 上游 0.32 做的是把这些 import 从 typing_extensions 收回 typing：
版本from typing import …from typing_extensions import …
0.24.0028 个文件
0.28.0032 个文件
0.32.037 个文件0

也就是说 requires-python 是这个清理动作的副产品，不是独立的技术决定。 补丁已拟好：packaging/vllm/patches/proposed/0002-py310-typing-and-stdlib-backport.patch （39 个文件——37 个 typing + 2 个 datetime，全在 vllm/ 内；tests/、tools/ 不进 wheel 故未动）， 与 0001 同机制、同挂载点。

实测（VLLM_TARGET_DEVICE=empty，源码树来自 filestore sdist）：

py3.10 + torch 2.11.0✅✅✅

empty wheel 亦已构建并安装成功： vllm-0.32.0+empty-cp310-cp310-*.whl（无 .so，纯 Python payload）， 装后三个入口 import 全通。构建只需改 1 行（pyproject.toml:34 的 requires-python），因为 pip 在 metadata 阶段就硬拦 py3.10；Linux 上 VLLM_TARGET_DEVICE=empty 会直接穿过设备自动探测分支（macOS 上的自动降级是本地取证 artifact）。

两个操作细节，供真正推进时用：
  • packaging/script/repack.py 只改 Requires-Dist，不动 Requires-Python。所以 +flagos wheel 会带着 >=3.11 出去， py3.10 后端 pip install 仍被拦。走 py3.10 路线需二选一：源码补丁里放松声明， 或给 repack 加一条 strip，或安装时 --ignore-requires-python。
  • runtime 是 uv venv /flagos --python ${PYTHON_VERSION}，一个后端只有一个 venv， 「同时带 3.10 和 3.12」在一个后端内不可行；抬版是整栈动作。

6.5 比 Python 更硬的地板：torch 2.7.1

vllm/ir/tolerances.py:32 在模块层直接引用 torch.float4_e2m1fn_x2， 而该 dtype torch 2.8 才出现。这条与 Python 版本无关，也不是 0.32 引入的： 该文件在 0.24.0 / 0.28.0 / 0.32.0 上 md5 完全相同（9498757d…）， 0.24 与 0.28 在 torch 2.7.1 上栽在同一行。

现有覆盖来自插件 —— vllm_fl/__init__.py:9-19 在任何 vllm.ir import 之前 注入哨兵（_torch.float4_e2m1fn_x2 = _torch.uint8）。实测这条路径确实成立： 用一个等价的 vllm.platform_plugins entry point 打在 site-packages 里， py3.10 + torch 2.7.1 上 EngineCore 与 api_server 均 import 通过 —— 说明 vLLM 装载插件早于 vllm.ir（worker_base.py:10 那个模块级 import vllm.ir 是插件装载之后才发生的）。

对 py3.10 七个后端的含义：只有 cambricon-neuware4.4.3（torch 2.7.1+cpu）需要这个垫片； hygon-dtk26.04 / kunlunxin（2.9.0）、mthreads×2（2.9.0 / 2.9.1）、sunrise / tsingmicro（2.11.0） 都在 2.8 之上。

§ 7
版本取舍

四个候选路径，按代价排序：

  1. 0.28.0 优先。同样 pin torch == 2.13.0，但 requires-python 仍是 >=3.10，7 个 py3.10 后端不必先迁 Python，一个补丁都不用。config.yaml 的 pin_indirect_per_version 已经为 0.28.0 / 0.32.0 两条都写好 xgrammar 0.2.8。
  2. 0.32.0 + torch 2.11 对 py3.12 后端成立：cambricon-neuware4.7.2、enflame-tops1.10.6、 nvidia-cuda13.3（均为 torch 2.11.0）。这是"torch 版本是唯一变量"的三个，仍需实测确认。
  3. 0.32.0 + py3.10 需要那条补丁常驻（§6.4）。技术上门已开（wheel 已构建、serve 入口已 import）， 但真实代价是维护面：偏离上游 CI 覆盖区间（0.32 只跑 3.11–3.14），补丁要跟每个新版本重打， 且 7 个后端要各跑一遍 F/T 验证。另有 Requires-Python 未 strip 的安装细节要一并处理。
  4. 0.32.0 + py3.10 + 抬后端 Python：最彻底，走 update-backend（vendor SDK 需提供 cp311/cp312 ABI + 重跑 runtime 与 app 验证），不是 app 版本推进能顺带完成的。
§ 8

grep -rn "float4_e2m1fn_x2" vllm-0.32.0/vllm/ir/tolerances.py
已做的验证：本机（macOS / arm64）在 py3.10 上完成 VLLM_TARGET_DEVICE=empty wheel 构建＋安装＋三个入口 import，并对 torch 2.7.1 / 2.8.0 / 2.9.0 / 2.11.0 各跑一遍； 补丁另经 patch -p1 --dry-run 与整树重放校验（应用后源码树与生成树逐字节相同）。
未做的验证：真实的 Linux 构建与 serve 实测 未执行——构建机上 Docker 无法访问任何 registry （reading HTTP CONNECT: unexpected EOF），本地 ubuntu 镜像无 python3 且 apt 源不可达；CUDA / 加速器路径完全未触达（host 为 macOS，仅有 CPU torch 构建）。 以上 py3.10 结论均为 import / metadata 级，不是推理级。

建议的关闸实验（若采纳 §7 路径 2 或 3）：在 enflame-tops1.10.6 （py3.12 / torch 2.11.0+cpu）或 cambricon-neuware4.7.2（py3.12 / torch 2.11.0+cpu）上跑一格 empty wheel 构建 + 单步安装 + serve；若要验路径 3，则换成任一 py3.10 后端（如 kunlunxin-xre5.37.1，torch 2.9.0+cpu）并挂上 0002 补丁。 两者都走 verify-app-backend 的流程，结果回写本文件。
